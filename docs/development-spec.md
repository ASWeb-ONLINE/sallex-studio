## 1. Контекст и точные границы результата

### 1.1. Идентификация проекта

- Название бренда в интерфейсе, метаданных и документации: **Sallex Studio**.
- Крупное написание на первом экране: **SALLEX**; дополнительная подпись: **STUDIO**.
- Ранее заданное техническое имя локальной папки: `site Solex Studio`. Это не новое название бренда.
- Используй фактическую подготовленную папку. Не переименовывай ее и не создавай внутри вторую папку с приложением без необходимости.
- Для нового удаленного репозитория предпочтительное имя: `sallex-studio`. Существующий корректный репозиторий и его имя сохраняются.
- Один сайт - один самостоятельный репозиторий. Рабочая папка является источником правды; отдельная экспортная копия для GitHub не нужна.

### 1.2. Что создаем

Собственный сайт авторской студии дизайна и разработки сайтов. Владелец проходит на нем полный цикл создания и обновления сайта до выполнения клиентских заказов.

Текущая версия нужна для проверки дизайна, поведения, адаптивности и процесса публикации. Это не этап подключения продаж, рекламы или обработки заявок.

Первая версия:

- одна законченная главная страница;
- служебная страница 404;
- работающая навигация и интерактивные элементы;
- GitHub-репозиторий исходников;
- автоматизированная публикация статической сборки через GitHub Pages;
- документация запуска, проверки, обновления и текущих ограничений.

Портфолио предусматривается архитектурно, но на опубликованном сайте пока полностью отсутствует.

### 1.3. Чего сейчас не делаем

Не добавляй блог, магазин, личный кабинет, платежи, CMS, базу данных, сервер приема заявок, CRM, чат-бота, рассылку, рекламные пиксели, аналитику, cookie-баннер ради декора, коммерческие юридические документы, домен или платный хостинг.

Не проводи новый нейминг, исследование конкурентов, цен или продвижения. Не расширяй публичное предложение до приложений, автоматизации и AI-консалтинга. Не внедряй дополнительные технологии ради демонстрации их наличия.

Максимальная проработка здесь означает качество композиции, взаимодействий, кода и проверки, а не максимальное количество функций.

## 3. Единая концепция первой версии

### 3.1. Визуальная формула

**Кинематографичный монохром + крупная плакатная типографика + строгая редакционная сетка + ограниченный красный акцент + свет, который локально проявляет цвет.**

Не делай сплошной черный сайт. Важна смена светлого и темного: крупные светлые композиции дают воздух, темные поверхности создают пространство для подсветки.

Первый экран должен восприниматься как графический плакат студии, а не как стандартный блок с заголовком слева и случайной иллюстрацией справа.

### 3.2. Рабочие решения для этой реализации

| Вопрос | Решение первой версии |
|---|---|
| Главный образ | Типографическая композиция без человека. Портрет не предоставлен и не обязателен |
| Первый экран | Светлый, с очень крупным SALLEX и ощущением слоев и направленного света |
| Цвет | Основной глубокий красный; бордовый используется как его темная теневая вариация |
| Световой эффект | Локальный фонарик на графических поверхностях, а не перекрашивание всей страницы |
| Структура | Главная с якорями, без отдельных страниц услуг на первом этапе |
| Услуги | Лендинг и сайт компании |
| Коммуникация | От лица автора, без вымышленной команды |
| Портфолио | Не публикуется, не заменяется концептами или фиктивными работами |
| Контакты | По умолчанию честный режим демонстрации без отправки данных; реальные ссылки только при наличии подтвержденных контактов |
| Стек при отсутствии уже выбранного | Astro, статическая сборка, TypeScript, собственные CSS и небольшие клиентские модули |
| Размещение | Исходники в GitHub, версия для просмотра в GitHub Pages |

Эти решения предназначены для получения одного цельного визуального кандидата. Не добавляй посетителю переключатель концепций, палитр или тем. Не делай несколько альтернативных сайтов вместо одного законченного.

Фотография владельца не требуется. Не генерируй случайного человека и не превращай отсутствие фото в пустой блок-заглушку.

## 5. Палитра и система визуальных параметров

Все повторяющиеся значения вынеси в дизайн-токены. Не разбрасывай вручную разные красные оттенки, радиусы, тени и длительности по компонентам.

### 5.1. Начальная палитра

| Токен | Значение | Назначение |
|---|---|---|
| `--color-paper` | `#EEECE8` | Светлые крупные секции |
| `--color-ink` | `#111111` | Основной текст и крупная типографика на светлом |
| `--color-night` | `#0D0D0D` | Темные секции |
| `--color-panel` | `#1B1B1B` | Поверхности внутри темных секций |
| `--color-text-inverse` | `#F2F0EC` | Текст на темном |
| `--color-muted-on-light` | `#625E5A` | Второстепенный текст на светлом |
| `--color-muted-on-dark` | `#AAA6A2` | Второстепенный текст на темном |
| `--color-accent` | `#C62836` | Основной красный акцент |
| `--color-accent-shadow` | `#7A2030` | Темная составляющая светового рефлекса, не основной цвет текста |

Это исходные значения единой палитры. Допустима небольшая коррекция по результатам проверки контраста и реального рендера. Изменения фиксируй в `docs/decisions.md`; не уходи в другую цветовую концепцию.

Красный в покое занимает небольшую часть композиции: деталь wordmark, номер, линия, маленький знак или состояние элемента. Не делай всю огромную надпись SALLEX красной по умолчанию. Не заливай большие секции бордовым.

Не используй основной красный для длинного мелкого текста на темном фоне. Такой текст должен быть светлым. Контраст проверяется и в покое, и при подсветке.

Радужные градиенты, фиолетово-синие свечения и дополнительные акцентные цвета не допускаются. Градиенты разрешены как светотень, маска и локальный красный свет, а не как самостоятельная разноцветная эстетика.

### 5.2. Типографика

Начальная пара: **Oswald** для крупной плакатной типографики и **Golos Text** для основного текста, навигации, форм и пояснений. Официальные источники семейств указаны в разделе 25.

- Для больших надписей используй плотные выразительные начертания, для текста - обычные и средние.
- Не набирай весь сайт капсом. Капс уместен в SALLEX, отдельных коротких заголовках и небольших рубриках.
- Основной текст на телефоне не меньше 16 CSS px; пояснения и метки обычно 13-14 px. Не копируй микроскопический масштаб подписей из референса.
- Длина текстовой строки обычно 45-70 знаков, без растягивания абзацев на всю ширину монитора.
- Межстрочный интервал текста ориентировочно 1.45-1.65, крупных заголовков 0.95-1.1. Не обрезай кириллицу и верхние элементы букв.
- SALLEX должен почти заполнять доступную ширину, сохраняя правильные пропорции букв. Подбери размер по реальному шрифту; не растягивай текст грубым `scaleX`.
- Не делай каждую букву отдельной бессмысленной анимацией.

Проверь кириллицу, цифры, нужные знаки и начертания в реально подключенных файлах. Используй легально доступные шрифты с сохранением лицензий и локальной раздачей вместе с сайтом или сборкой из зафиксированных пакетов. Не делай загрузку внешнего Google Fonts API обязательной для посетителя.

### 5.3. Сетка, отступы, поверхности

- На широком экране основная сетка 12 колонок; контент ориентировочно до 1320-1440 px, фоны секций на всю ширину.
- Боковые поля на настольном экране обычно 48-64 px, на планшете 28-32 px, на телефоне 20-24 px; на 320 px допустимо 16 px.
- Вертикальные интервалы крупных секций ориентировочно 88-128 px на настольном экране и 56-72 px на телефоне.
- Основные кнопки высотой не менее 48 px; интерактивная зона небольших элементов не менее 44 на 44 px как проектная цель.
- Радиусы преимущественно 0-4 px. Не используй повсюду капсулы, мягкие SaaS-карточки и большие скругления.
- Тонкие разделители, четкие края, небольшое количество осмысленных поверхностей.

Эти числа - ориентиры, не повод ломать композицию на промежуточной ширине. Контент, переносы и удобство важнее буквального сохранения фиксированной высоты.

## 6. Карта главной страницы

Последовательность первой версии:

1. Шапка и навигация.
2. Светлый первый экран с крупной типографической композицией.
3. Темная секция «Форматы сайтов» с двумя большими интерактивными поверхностями.
4. Светлая секция «Подход».
5. Секция «О студии» с собственной типографической композицией, без обязательного фото.
6. Светлая или нейтральная секция вопросов, связанная с предыдущим блоком общей сеткой.
7. Темная контактная секция.
8. Компактный подвал.

Будущее портфолио вставляется между форматами сайтов и подходом. При отсутствии опубликованных работ его нет ни в разметке, ни в меню, ни в графическом ритме страницы.

Меню: **Услуги · Подход · О студии · Контакты**.

Якоря: `#services`, `#approach`, `#about`, `#contact`. Вопросы можно адресовать через `#faq`, не добавляя отдельный пункт меню.

Все разделы должны выглядеть частью одной системы. Не собирай страницу из разных стилевых «лендингов внутри лендинга».

## 7. Подробная режиссура разделов и тексты

Тексты ниже - готовая редакционная основа первой версии, а не утверждение о накопленном опыте студии. Можно умеренно править переносы и сокращать отдельные предложения, сохраняя смысл. Не добавляй новые факты, обещания или услуги.

### 7.1. Шапка

Слева wordmark Sallex Studio, в центре или справа навигация, отдельное основное действие «Обсудить проект».

Шапка легкая, без черной служебной полосы ради копирования игрового сайта. Допустима тонкая линия снизу. На настольном экране ориентировочная высота 76-88 px, на телефоне 64-72 px.

Wordmark возвращает в начало страницы. Кнопка ведет к `#contact`, пункты меню - к соответствующим разделам. Ссылки работают и без анимации прокрутки.

Можно использовать спокойную липкую шапку. Она не должна перекрывать якорный заголовок или заметную часть маленького экрана. Не добавляй уменьшение, исчезновение и появление шапки по сложной кинематике.

На телефоне реализуй компактное меню. Предпочтительна простая раскрывающаяся панель, а не полноэкранный спецэффект. У кнопки есть понятное имя и состояние; Escape и выбор ссылки закрывают меню, фокус не теряется.

### 7.2. Первый экран

**Рубрика:** «АВТОРСКАЯ ВЕБ-СТУДИЯ».

**Композиционная надпись:** «SALLEX» и небольшая «STUDIO».

**Единственный H1:** «Дизайн и разработка сайтов».

**Описание:**

> От структуры и визуальной идеи до готового сайта. Проект веду лично: продумываю логику, создаю дизайн и собираю работающую версию.

**Основное действие:** «Обсудить проект» -> `#contact`.

**Второе действие:** «Как я работаю» -> `#approach`.

Композиция:

- молочно-светлая поверхность;
- очень крупное почти черное SALLEX на большей части ширины;
- рубрика и короткие пояснения расположены асимметрично по сетке;
- видимая глубина создается аккуратной работой с самой типографикой: срезом света, направленной тенью или небольшим смещением графического слоя;
- один небольшой постоянный красный знак или линия;
- блок описания и действий не перекрывает буквы и не теряется среди графики;
- начало следующей темной секции должно естественно приглашать к прокрутке.

Не добавляй случайную статую, человека, хромированный шар, ноутбук со стоковым экраном или коллекцию бессмысленных 3D-объектов. Главный образ здесь - сама типографика.

Нужна сложенная композиция, а не просто слово большим шрифтом по центру пустого экрана. Используй крупный масштаб, точные выравнивания, соотношение пустоты и текста, небольшое число слоев. Не компенсируй отсутствие решения количеством декора.

На широком экране первый экран ориентировочно занимает 0.85-1.05 высоты окна вместе с шапкой, но не используй жесткую высоту, обрезающую содержимое. На низком экране уменьшай пустые интервалы, а не читаемость текста.

На телефоне SALLEX остается читаемым целиком в одну строку; описание и кнопки переходят ниже. Не переносить бренд по буквам. Дополнительные слои упрощаются, а не складываются поверх контента.

Можно добавить умеренное локальное проявление красного на фрагменте надписи при движении курсора. Это вторичный эффект: герой должен выглядеть завершенным до первого движения мыши.

### 7.3. Форматы сайтов

**Рубрика:** «01 / УСЛУГИ».

**H2:** «Сайт под вашу задачу».

**Вводный текст:**

> Для одного предложения или для компании с несколькими направлениями. Формат выбирается по содержанию и тому, что посетитель должен сделать на сайте.

Две крупные прямоугольные поверхности рядом на настольном экране и друг под другом на телефоне. Не заменяй их шестью маленькими карточками с одинаковыми иконками.

**Первая поверхность: «Лендинг».**

> Одна услуга, продукт или предложение. Последовательная страница, на которой понятно, что вы предлагаете и как с вами связаться.

Короткие составляющие: «Структура», «Дизайн», «Адаптивная сборка».

Действие: «Обсудить лендинг» -> `#contact` с выбором соответствующего типа проекта в локальной форме, если JavaScript доступен.

**Вторая поверхность: «Сайт компании».**

> Несколько услуг и больше информации о бизнесе. Связанная структура страниц, в которой легко найти нужное и понять следующий шаг.

Составляющие: «Разделы и навигация», «Единая визуальная система», «Основа для развития».

Действие: «Обсудить сайт компании» -> `#contact` с соответствующим выбором типа.

Графика:

- для лендинга - оригинальная абстрактная композиция одной страницы из крупных графических зон;
- для сайта компании - несколько связанных плоскостей или страниц;
- это схемы формата, не скриншоты несуществующих клиентских работ;
- поверхности и детали в покое монохромны, кроме малых общих акцентов;
- в зоне света у графики проявляется красная или бордовая составляющая, за ее пределами сохраняется монохром;
- текст и действия остаются читаемыми постоянно.

Этот раздел - основное место демонстрации фирменного светового эффекта уже в первой версии. Нельзя отложить всю колоризацию до будущего портфолио.

Не делай всю поверхность ложной ссылкой, если действие есть только у кнопки. Не меняй курсор на pointer там, где нажатие ничего не делает. Не вкладывай кнопку внутрь другой ссылки.

### 7.4. Подход

**Рубрика:** «02 / ПОДХОД».

**H2:** «От задачи до работающего сайта».

Светлый фон, крупные номера и четыре последовательные строки или секции с тонкими разделителями. Не еще одна сетка одинаковых карточек.

**01. Понять задачу.**  
«Разбираемся, что нужно рассказать о бизнесе, кому адресован сайт и какое действие важно для посетителя».

**02. Собрать структуру.**  
«Определяем разделы, порядок информации и содержание. Убираем лишнее до начала детальной отрисовки».

**03. Найти визуальное решение.**  
«Собираем типографику, цвет, изображения и поведение элементов в цельную систему».

**04. Собрать и проверить.**  
«Переносим дизайн в работающий сайт, проверяем разные экраны, действия и публикацию».

Допустимы сдержанные появления при прокрутке и небольшой цветовой акцент на номере. Эффект фонарика здесь не обязателен. Текст не скрывать до наведения.

### 7.5. О студии

**Рубрика:** «03 / О СТУДИИ».

**H2:** «Один контакт. Цельный процесс».

**Текст:**

> Sallex Studio - мой авторский проект. Меня зовут Александр Сальников. Со мной вы обсуждаете задачу, согласовываете визуал и принимаете готовый сайт.
>
> Я связываю структуру, дизайн и разработку в один процесс, чтобы решения не терялись между отдельными этапами.

Составь асимметричный блок: крупная собственная типографическая композиция с одной стороны, текст с другой. Возможно графитовое поле, мягкий свет и крупный фрагмент SALLEX как материал композиции. Не повторяй первый экран буквально.

Не добавляй вымышленные годы опыта, количество сайтов, рейтинг, награды, офис, команду или логотипы клиентов. Не переноси сюда сведения о другой работе владельца. Не вставляй фиктивный портрет и не оставляй место «фото скоро».

### 7.6. Вопросы

**H2:** «Несколько вопросов до старта».

Компактный accordion на основе доступной семантики. Все вопросы читаются сразу. Ответы доступны с клавиатуры; одновременно могут быть открыты несколько ответов. Нет необходимости закрывать один только из-за открытия другого.

**Что нужно для начала?**  
«Описание задачи и информация о вашем бизнесе. Если уже есть тексты, фотографии, логотип или действующий сайт, они помогут определить объем работы».

**Можно начать без готовых текстов?**  
«Да. Сначала определим, какую информацию нужно собрать. Факты о бизнесе и содержание будущего сайта согласуем до публикации».

**Будет ли сайт удобен с телефона?**  
«Мобильная версия продумывается вместе с основной. Навигация, размеры текста и действия проверяются на разных размерах экрана».

**Как согласуются изменения?**  
«Сначала фиксируем задачу, структуру и визуальное направление. Состав работ и порядок согласований определяем до начала проекта».

**Можно развивать сайт после запуска?**  
«Да. Можно добавлять материалы, страницы и новые возможности. Объем следующих изменений определяется отдельно».

Не добавляй ответы с неподтвержденными ценами, сроками, числом бесплатных правок и гарантиями продаж.

### 7.7. Контактная секция

**Рубрика:** «04 / СЛЕДУЮЩИЙ ШАГ».

**H2:** «Обсудим ваш сайт».

**Описание:**

> Расскажите, что за бизнес, какой сайт нужен и какую задачу он должен решить.

Темный завершающий блок. Слева крупный заголовок и пояснение, справа компактная интерфейсная область. На телефоне - последовательная вертикальная композиция.

По умолчанию используй режим `contactMode: 'preview'`:

- поле «Формат сайта»: «Лендинг», «Сайт компании», «Пока не определился»;
- поле «О задаче»: многострочный текст;
- действие «Скопировать описание»;
- рядом с интерфейсом отчетливая, но визуально спокойная подпись: «Демо-режим: текст не отправляется и не сохраняется сайтом»;
- сообщение об успешном действии только после фактического копирования: «Описание скопировано»;
- при отказе Clipboard API покажи сформированный текст для ручного выделения и копирования;
- не очищай введенное после ошибки;
- без запросов на сервер, аналитики, localStorage, cookies и фонового сохранения содержимого.

Это не форма приема заявки. Не проси имя, телефон и email в режиме preview. Не называй кнопку «Отправить», не показывай фиктивное «Заявка получена» и не записывай текст в URL.

Если в подготовленных материалах уже есть явно согласованные публичные контакты Sallex Studio, разрешен режим `contactMode: 'direct'`: настоящие ссылки на почту или мессенджер, плюс при необходимости локальная подготовка описания. Не подключай сторонний обработчик и не отправляй сообщения автоматически. Состав контактов должен храниться в одном конфигурационном файле.

Наличие или отсутствие контактов не должно ломать дизайн или останавливать сборку. Не используй выдуманные адреса, номера и никнеймы.

### 7.8. Подвал

Wordmark, короткая подпись «Дизайн и разработка сайтов», компактная навигация и небольшой маркер «Версия для просмотра».

Год формируется при сборке. Ссылка на GitHub допустима только после появления настоящего URL репозитория и при подходящей видимости. Не добавляй ряд пустых иконок социальных сетей.

Не показывай ссылки на несуществующую политику, договор, портфолио или страницу услуг. Неподключенные функции просто отсутствуют.

### 7.9. Страница 404

В той же палитре и типографике: крупное «404», текст «Такой страницы нет», рабочая кнопка «На главную». Ссылка учитывает базовый путь проекта GitHub Pages.

Страница ошибки остается легкой. Не запускай на ней тяжелую графику и не перенаправляй автоматически на главную, маскируя ошибку.

## 8. Портфолио: готовность к расширению без фиктивного содержания

Предусмотри минимальную модель проекта: slug, название, сфера, задача, роль, выполненные работы, изображения, URL, результат с источником при наличии, разрешение на публикацию и статус `draft/published`.

На текущем этапе список опубликованных проектов пуст.

Условие появления раздела: есть минимум один реальный проект со статусом published и разрешением владельца на публикацию. Фильтрация должна происходить на этапе сборки, до формирования HTML, маршрутов и клиентских данных.

Не импортируй черновые кейсы в клиентский bundle и не прячь их только через CSS. Не создавай публичные страницы `/works/...` для пустых или черновых данных. Не выводи пункт меню, заголовок, счетчик 0, карточки «скоро», примеры клиентов и фиктивные результаты.

Достаточно небольшой типизированной модели, точки подключения раздела и документации добавления настоящего кейса. Не создавай CMS и универсальный конструктор портфолио.

Для будущего раздела зафиксируй правило: монохромное превью может локально проявлять реальные цвета работы при наведении. Внутри будущего кейса проект показывается в исходных цветах, а не искусственно обесцвечивается.

## 9. Подсветка и локальная колоризация: обязательный эффект

### 9.1. Суть

Нужно ощущение, что курсор освещает поверхность в полумраке. Свет проявляет материал и цвет только рядом с собой. Это не обычный hover, при котором вся карточка сразу становится цветной, и не полупрозрачный кружок поверх всего сайта.

Разделяй три независимых слоя:

1. Базовая монохромная графика или поверхность.
2. Та же графика с красной/бордовой составляющей, видимая через локальную мягкую маску.
3. Очень умеренный световой рефлекс поверхности или границы.

Контент и кнопки находятся в отдельном читаемом слое. Декоративные дубли не должны дважды читаться скринридером.

### 9.2. Состояния

| Состояние | Требуемое поведение |
|---|---|
| Нет наведения | Монохромная графика, спокойная поверхность, все названия и действия видимы |
| Курсор вошел | Свет появляется именно в точке входа, без вспышки в углу или центре |
| Курсор движется | Пятно и маска перемещаются по поверхности, цвет проявляется локально |
| Курсор остановился | Свет остается на месте, нет пульсации и бесконечного холостого движения |
| Курсор вышел | Цвет и свечение плавно исчезают, исходное состояние восстанавливается |
| Фокус клавиатуры | Четкий focus-visible и при необходимости статическое подсвеченное состояние |
| Touch / coarse pointer | Законченный статический вариант с небольшим цветовым акцентом, без слежения за пальцем |
| Reduced motion | Статический вариант без движения маски, параллакса и анимированного скролла |
| JavaScript недоступен | Все содержание и основные действия доступны, эффект не требуется |
| Маска не поддерживается | Спокойное статическое состояние или простое изменение акцента без потери контента |

### 9.3. Визуальные параметры

Начальные ориентиры:

- радиус мягкой области проявления на крупной поверхности: примерно 160-240 CSS px;
- световой ореол немного шире области насыщенного цвета;
- граница пятна плавная, без четкого обода;
- появление 160-220 мс;
- затухание 280-400 мс;
- движение следует за курсором практически сразу; длинный инерционный хвост запрещен;
- интенсивность позволяет отчетливо заметить цвет, но не превращает поверхность в неоновую вывеску.

Радиус подбирай по фактической геометрии. Пятно не должно обесцвечивать или окрашивать весь блок при любом наведении. Красный свет не должен смывать контраст текста.

В исходном состоянии на больших темных поверхностях должна читаться графика. Не делай «ничего не видно, пока не нашел фонариком».

### 9.4. Область применения

Обязательно: обе поверхности услуг.

Допустимо умеренно: крупная типографика первого экрана и один декоративный фрагмент раздела о студии.

Не нужно: отдельный фонарик у каждого слова, FAQ, всех кнопок и обычных текстовых абзацев. Не добавляй глобальный красный диск, следующий за мышью поверх всей страницы.

Обычный системный курсор сохраняется. Кнопки не убегают за мышью и не притягивают ее к центру.

### 9.5. Технические ориентиры

Реализуй эффект небольшим переиспользуемым модулем на Pointer Events, CSS-переменных, градиентной маске и при необходимости `requestAnimationFrame`. CSS `mask-image` допускает градиентную маску [Т4]; использование кадрового API сверяй с документацией [Т5].

Не обязателен WebGL, Canvas, Three.js, GSAP, Framer Motion или анимационный React-runtime.

- Отслеживай координаты относительно активной поверхности, а не всего окна.
- Корректно пересчитывай геометрию после прокрутки, resize и изменения размеров элемента.
- Не вызывай множество принудительных layout-чтений и записей на каждом событии.
- Объединяй обновления в один кадр. Не держи бесконечный активный цикл, когда ничего не меняется.
- Отключай обработчики и кадры для неактивного эффекта, скрытой вкладки и reduced motion.
- Учитывай изменение системной настройки движения без обязательной перезагрузки.
- Декоративные слои имеют `pointer-events: none`, не перехватывают клики и выделение текста.
- Не применяй `filter: grayscale(1)` к общему родителю, внутри которого должен остаться цветной слой.
- Цветной и монохромный слой совпадают по размерам, обрезке и положению; при движении не возникает двойных контуров.
- При нескольких SVG-композициях ID масок, градиентов и clipPath уникальны.
- Не создавай скрытые полноразмерные копии всей страницы ради эффекта.
- Не запрашивай pointer lock и не скрывай системный курсор.

Для включения следящего эффекта используй характеристики устройства, например сочетание `hover: hover` и `pointer: fine`, и настройку движения, а не только ширину экрана. Конкретное поведение гибридных устройств проверь отдельно [Т6, Т7].

### 9.6. Проверяемый критерий

На одной и той же поверхности сделай четыре состояния: покой, курсор слева, курсор справа, после ухода.

Сравнение должно показывать, что цветная область действительно переместилась, часть графики вне пятна осталась монохромной, а после ухода исходный вид восстановился. Изменение только значения CSS-переменной не является достаточной проверкой визуального эффекта.

## 10. Остальные движения и микровзаимодействия

Разрешены короткие изменения подчеркивания, заливки, тонкой границы, положения стрелки и аккуратное однократное появление некоторых секций.

Начальные параметры: обычные состояния 160-240 мс; появления крупных элементов 350-500 мс; смещение при появлении не больше примерно 12-20 px.

Не используй обязательный загрузочный экран, захват прокрутки, горизонтальную прокрутку вместо вертикальной, бесконечные бегущие строки, звуки, фоновое видео, частицы, мигание, дым и чрезмерный параллакс.

Контент присутствует и виден без инициализации анимационной библиотеки. Ошибка JavaScript не должна оставить страницу с `opacity: 0`.

Hover, active и focus-visible различаются. Нажатие не должно вызывать layout shift из-за изменения толщины границ или размеров текста.

## 15. Git и безопасность публикации исходников

### 15.1. Сохранность

Не делай `reset --hard`, принудительный push, удаление репозитория, перезапись истории, массовую очистку, изменение чужих remotes или переименование существующих веток без необходимости и разрешения.

При наличии незакоммиченных изменений сначала разбери, какие принадлежат проекту и владельцу. Не затирай их и не включай постороннее в свой коммит.

### 15.2. Исключения из Git

Проверь `.gitignore` и фактический индекс. Как минимум не должны публиковаться:

- секреты, `.env` и локальные варианты с разрешенным обезличенным `.env.example` при необходимости;

Правило ignore не удаляет уже отслеживаемый файл. Если такой файл обнаружен, сначала разберись с его статусом; не заявляй об отсутствии утечки только потому, что добавил строку в `.gitignore`.

Не выбирай публичную open-source лицензию для всего проекта без отдельного решения владельца. Лицензии используемых сторонних компонентов и шрифтов сохраняются.

## 17. GitHub Pages и автоматическая публикация

### 17.1. Публикуем статическую сборку

Настрой Pages через GitHub Actions. В удаленном репозитории должен быть выбран соответствующий источник публикации. Не отправляй владельца вручную загружать архив и не создавай вторую папку сайта для Pages.

Используй актуальный официальный путь для статической сборки Astro или эквивалент выбранного стека. Поддерживаемые действия и требования к их правам описаны в документации [Т1, Т3].

Не фиксируй версии actions наугад по памяти. Во время выполнения проверь официальные стабильные версии, совместимость Node.js и runner; закрепи используемые версии, при возможности точные проверенные SHA. Не используй случайные сторонние deploy-actions вместо официальных без причины.

### 17.2. Логика workflow

Workflow должен:

1. Выполняться при push в основную ветку и вручную через `workflow_dispatch`.
2. Получать исходники, устанавливать согласованную Node.js и зависимости из lock-файла.
3. Выполнять проверки типов, браузерные smoke-проверки и статическую сборку. Браузерные проверки могут использовать build/preview согласно конфигурации тестов.
4. Не публиковать результат при провале обязательной проверки.
5. Загружать только готовый каталог сайта как Pages artifact, не весь репозиторий.
6. Развертывать проверенный artifact через окружение `github-pages`.
7. Возвращать фактический URL deployment.
8. Исключать конфликтующие одновременные деплои одного окружения.

Если добавлены проверки для pull request, они не должны автоматически публиковать непроверенный код в основное Pages-окружение. Не используй `pull_request_target` ради упрощения доступа к правам.

Разрешения минимальные: чтение исходников для сборки, `pages: write` и `id-token: write` только там, где требуется публикация. Обычный workflow Pages не должен требовать сохранения личного токена владельца в коде [Т3].

Не включай платное потребление и не меняй лимиты аккаунта. Нехватку разрешений или доступной квоты фиксируй как конкретное внешнее препятствие.

### 17.3. Базовый путь проекта

Project Pages обычно размещает сайт в подпути вида `/<repository>/`, а не в корне домена. В Astro для этого используются фактические `site` и `base`; прямые внутренние пути должны учитывать базу [Т1].

Требования:

- владелец, имя репозитория и URL берутся из реально выбранного проекта, не из выдуманного username;
- один согласованный способ формировать пути к графике, шрифтам, favicon, странице 404 и внутренним страницам;
- якорные ссылки внутри главной не отправляют посетителя в корень аккаунта;
- нет случайных `/assets/...` или `/fonts/...`, обходящих подпуть;
- после обновления страницы любой существующий URL работает;
- 404 ссылается на настоящую главную проекта;
- метаданные и обложка ссылки имеют корректные пути;
- локальная проверка включает сборку с тем же непустым base path, что будет на Pages;
- при будущем переносе на другой хостинг базовый путь меняется в одном месте, а не массовой заменой строк.

Не исправляй ошибки путей SPA-трюком с перенаправлением всех 404 на index. Для этой статической страницы такой обход не нужен.

### 17.4. Проверка после публикации

После push дождись окончания реального workflow. Проверь, что успешный запуск относится именно к нужному commit, а не к старой версии.

Открой адрес из результата deployment или API Pages и проверь:

- главная отвечает и содержит текущую версию;
- CSS, JavaScript, шрифты и изображения загружаются без 404;
- навигация и якоря работают в подпути;
- фонарик работает не только локально;
- мобильное меню и FAQ работают;
- preview-интерфейс ничего не отправляет;
- неизвестный адрес открывает корректную 404, а кнопка возвращает на главную;
- нет консольных ошибок и смешанного контента.

Исправь обнаруженные дефекты, опубликуй новую версию и повтори проверку. Не выдавай предполагаемый Pages URL за готовый результат до проверки.

Не обещай проверку доступности из России без VPN, если не проверял именно такой маршрут. Сайт не должен зависеть от необязательных внешних сервисов, но доступность конкретной сети необходимо отличать от этого архитектурного свойства.

## 18. Обязательная техническая проверка

Проверяй production-сборку, а не только dev-сервер.

Минимальный набор:

- воспроизводимая установка по lock-файлу;
- успешная проверка типов и шаблонов;
- успешная статическая сборка;
- отсутствие необработанных ошибок в консоли браузера;
- отсутствие проваленных запросов на необходимые ресурсы;
- корректные относительные и базовые пути;
- отсутствие горизонтального переполнения на контрольных ширинах;
- рабочее меню, якоря и FAQ;
- локальное копирование с обработкой отказа доступа к буферу;
- отсутствие сетевой отправки и хранения введенного описания;
- отсутствие portfolio-раздела, пустых кейсов и их данных в сборке;
- отсутствие контактов-заглушек, lorem ipsum и неподтвержденных чисел;
- корректные meta и noindex для preview;
- клавиатурная навигация, reduced motion, touch и вариант без JavaScript;
- корректная 404;
- чистый от секретов и чужих референсов набор публикуемых файлов.

Браузерные тесты реализуй через Playwright или уже имеющийся равноценный инструмент. Инструмент должен действительно запускать браузер. Загрузка HTML через HTTP и поиск строк не заменяют проверку рендера.

Не отправляй тестовые сообщения реальным адресатам. Тестировать разрешено локальное поведение, ссылки без реальной отправки и собственную опубликованную страницу.

## 19. Обязательная визуальная проверка

Успешная сборка не означает, что дизайн готов. Проведи минимум два визуальных прохода: оценку первой полной реализации и проверку после исправлений.

### 19.1. Набор скриншотов

Сохрани локально:

- полный вид страницы на 1440 x 900;
- первый экран отдельно на 1440 x 900 и 1366 x 768;
- полный мобильный вид на 390 x 844;
- первый экран на 320 px ширины;
- планшетный вид;
- поверхности услуг в покое, с курсором слева, справа и после ухода;
- открытое мобильное меню;
- FAQ с открытым ответом;
- контактный preview после успешного копирования или в состоянии ручного копирования;
- вид с reduced motion и контрольный keyboard focus.

Playwright поддерживает полноразмерные снимки страниц и снимки отдельных элементов [Т13]. Дождись загрузки шрифтов. Для общих снимков устрани случайное влияние движения, а интерактивные состояния снимай отдельно после нужного события.

Не подменяй реальный рендер нарисованным макетом. Не называй эмуляцию телефона проверкой на настоящем телефоне. При недоступности браузера явно укажи, что визуальная приемка не выполнена; не утверждай обратное.

### 19.2. Что оценить глазами

- Первый экран узнаваем и собран, а не пустая заготовка с одним большим словом.
- SALLEX имеет достаточный масштаб, описание деятельности не теряется.
- Светлые и темные участки образуют понятный ритм, а не случайную полосатую страницу.
- Красный в покое действительно остается небольшим акцентом.
- Поверхности услуг не выглядят плоскими пустыми прямоугольниками.
- Колоризация заметна как изменение графики, а не только как красное размытие поверх нее.
- Служебные подписи, тонкие линии и текст не становятся чрезмерно мелкими.
- Кнопки расположены логично и читаются без поиска курсором.
- Разделы различаются по композиции, но не по общему стилю.
- Мобильный сайт выглядит специально собранным для телефона, а не сжатым настольным.
- Нет случайных переносов, одиноких слов, наложений и обрезанных фрагментов.
- Нет необъяснимого пустого места на месте отсутствующего портфолио или фото.

Исправления делай по конкретным наблюдениям. Не ограничивай отчет субъективным «выглядит премиально».

## 21. Что считается неуспешной реализацией

Не принимать за завершение:

- стандартный шаблон агентства, только перекрашенный в черный и красный;
- интерфейс из одинаковых скругленных карточек с произвольными иконками;
- один красивый первый экран при незавершенной остальной странице;
- эффект, который существует в коде, но почти не виден в браузере;
- перекрашивание всей карточки вместо локального проявления;
- глобальный светящийся курсор, мешающий интерфейсу;
- скрытый до наведения смысловой текст;
- хорошую настольную версию при сломанном телефоне;
- фиктивную отправку заявки;
- пустое портфолио или подставные кейсы;
- публикацию только build-архива вместо исходников;
- успешный локальный запуск при сломанных путях GitHub Pages;
- отчет о деплое без успешного workflow и открытия действительного URL;
- завершение словами «осталось только проверить», если необходимые инструменты доступны.

## 22. Порядок выполнения

### Этап A. Обследование и обновление статуса

Прочитай проект, проверь файлы, Git и инструменты. Переведи проектные инструкции в новый этап. Сохрани это ТЗ и короткий план. Установи фактические ограничения и не допускай потери подготовленных материалов.

### Этап B. Реальная визуальная основа

Подключи типографику, токены и сетку. Сделай первый экран и обе поверхности услуг сразу с мобильным вариантом. Реализуй работающий световой эффект на одной поверхности, проверь его и перенеси на вторую.

Не трать весь ресурс на документацию и настройки, откладывая визуал на конец. Сначала должна появиться проверяемая композиционная основа.

### Этап C. Вся страница

Собери подход, блок автора, FAQ, контактный preview, подвал, меню и 404. Проверь навигацию и адаптивность. Предусмотри портфолио без публичного содержания.

### Этап D. Визуальная доводка и тесты

Открой production-сборку, сделай скриншоты, оцени композицию, исправь размеры, отступы, переносы, свет и состояния. Выполни автоматические и ручные проверки. Не выдавай первую сборку за финальный внешний вид.

### Этап E. GitHub и Pages

Проверь файлы для публикации, реши только реальные вопросы доступа и видимости, выполни коммиты и push, настрой workflow и Pages. Дождись результата и проверь опубликованный сайт. При необходимости исправь и выпусти обновление.

### Этап F. Передача

Актуализируй README, инструкции обновления, реестр решений и отчет проверки. Верни ссылки и локальные материалы просмотра. Не заявляй, что владелец уже принял дизайн: это завершенная реализация для его оценки.

## 24. Формат финального ответа Codex

Верни короткий, но предметный отчет:

1. Точный локальный путь проекта.
2. Что реализовано визуально и какой главный образ получился.
3. Где работает фонарик, как проявляется цвет и что происходит на touch/reduced motion.
4. Настоящий URL GitHub-репозитория и его видимость.
5. Настоящий URL GitHub Pages, статус workflow и идентификатор проверенного commit.
6. Ссылки или пути к настольным и мобильным скриншотам, отдельно к состояниям эффекта.
7. Результаты check/build/браузерных и визуальных проверок, без выдуманных измерений.
